Um cérebro, vários repositórios: governança comum para todos os seus projetos com IA

Com vários projetos, o problema não é só cada agente esquecer. É cada projeto ter o seu próprio jeito. Um cérebro compartilhado dá o mesmo padrão a todos, sem misturar o que é de cada um.

Alfredo R. CâmaraCriador do AI Second Brain
📅 2 de Novembro de 2026·⚡ Arquitetura & Governança

Imagine três repositórios com três jeitos diferentes de commitar, três políticas de segurança e três formas de decidir quando chamar uma IA. Cada agente trabalha bem dentro do seu projeto, e o conjunto vira uma colcha de retalhos. O AI Second Brain resolve isso separando o que é comum a todos do que é específico de cada projeto.

01 · O QUE É COMUMAs camadas compartilhadas por todos os projetos

Regras inegociáveis
.agents/rules/: desenvolvimento, segurança, roteamento de IA e documentação.
Skills do agente
.agents/skills/: gate de IA, onboarding de projetos, revisão arquitetural e persistência de memória.
Base de conhecimento
knowledge/: padrões universais, como AI Gateway, AIJev, OWASP e arquitetura.
Memória e decisões globais
memory/ com estado atual e lições aprendidas, e decisions/GLOBAL_DECISIONS.md.

02 · O QUE É DE CADA UMCada projeto tem a sua pasta de contratos

projects/<nome>/├── PROJECT.md # visão e escopo├── ARCHITECTURE.md # arquitetura formalizada├── CURRENT_STATE.md # onde o projeto está hoje├── DECISIONS/ # ADRs do projeto├── BACKUPS/ # exportações em Markdown e JSON└── RESEARCH/ # laboratórios de pesquisa

A memória fica em dois níveis: a do framework, comum a todos, e a de cada projeto, em projects/<nome>/. Assim o contexto de um cliente não vaza para o de outro.

03 · UM PROJETO NOVOEntra no cérebro em poucos minutos

Você pode criar o projeto do zero, com git init automático, ou vincular um repositório que já existe por junção NTFS ou symlink, sem duplicar arquivos. A skill project-onboarding cria a estrutura padronizada e os contratos iniciais (PROJECT, ARCH, STATE e ADR-0001), que você revisa antes de gravar.

Criar ou vincular o repositório→Sabatina sobre a stack→Contratos preenchidos→Projeto herda regras e skills comuns

04 · A ROTINAAlternar entre projetos sem perder o fio

A cada troca de projeto, você diz ao agente em qual vai trabalhar e pede o contexto atual. Ele lê o PROJECT.md, o CURRENT_STATE.md, as decisões e as memórias anteriores, e devolve um resumo. No fim, a skill session-memory registra a sessão. Os dois checklists do projeto:

Início da tarefa
  • Ler o PROJECT.md e o CURRENT_STATE.md do projeto.
  • Verificar as regras em .agents/rules/.
  • Classificar a tarefa antes de agir.
Encerramento da sessão
  • Testar as alterações.
  • Atualizar o CURRENT_STATE.md do projeto.
  • Atualizar a memória persistente global.
  • Registrar decisões em DECISIONS/.

05 · GLOBAL OU LOCALOnde cada decisão e cada lição deve morar

As lições registradas na memória global ficam disponíveis para as próximas sessões, e as decisões que valem para todos os projetos vão para GLOBAL_DECISIONS.md. As que valem só para um vão para o DECISIONS/ do projeto.

Um teste que eu uso, e que não é regra do projeto: se a decisão continuaria valendo caso você trocasse de projeto amanhã, ela é global. Se não, é local. Para ver todos os projetos de uma vez, o portal tem um dashboard com o status de governança e um grafo 3D em que cada projeto é uma estrela com seus arquivos orbitando.

06 · LIMITES HONESTOSO preço de ter um cérebro só

Uma regra errada afeta todos
Mudar uma regra global muda o comportamento de todos os projetos. Registre a mudança como ADR.
Regra demais engessa
Projetos com necessidades diferentes podem sofrer com padrões globais rígidos. Mantenha o comum enxuto.
Exige disciplina
Os checklists de início e de encerramento só funcionam se forem feitos, em todos os projetos.
0camadas comuns
0itens por projeto
0níveis de memória
O que é comum vira padrão. O que é de cada um continua sendo de cada um.
