Quando NÃO usar LLM: o portão de decisão que poupa tokens e latência

Determinística, decisão ou geração: as 3 faixas para decidir quando chamar um modelo e parar de pagar token por aquilo que uma regra simples resolve.

AC
Alfredo R. Câmara Criador do AI Second Brain
📅 22 de outubro de 2026 · ⚡ AI Decision Gate & JEV

Muita gente acredita que “adicionar IA” ao produto significa disparar um POST para uma API de chat a cada clique do usuário. É o que o guia técnico do projeto chama de Anti-Padrão do LLM Ingênuo. Funciona na demonstração. Em produção, cobra em dinheiro, em segundos e em confiabilidade. Neste artigo mostro o contrapeso que adotei no AI Second Brain: um portão de decisão que resolve localmente tudo o que não precisa de um modelo.

01 · O PROBLEMAO que o LLM ingênuo custa

Fatura sem necessidadeCada requisição paga tokens de entrada e saída, mesmo quando uma regra simples resolveria.
LatênciaCerca de 1,2 a 3,5 segundos por chamada, entre rede e inferência, a cada interação do usuário.
Alucinação em regra de negócioRespostas inconsistentes onde só deveria existir uma resposta correta, como aprovar ou recusar uma transação.
Rate limit e quedasErros 429 ou 503 do provedor derrubam o fluxo inteiro se não houver alternativa local.

Sem Portão de Decisão (LLM Ingênuo)

“Valide se este CPF é válido e formate como 000.000.000-00.”
“Processando... [Chamando GPT-4o: 1.450 tokens prompt + 280 completion. Latência: 1.820ms. Custo: $0.009] O CPF informado é válido e formatado.”
“Repita isso para os 50.000 clientes da base.”
⚠️ ~86 milhões de tokens desperdiçados, US$ 450 de fatura de API e 25 horas de latência acumulada para algo que uma regex resolve em 0 ms.

Com AI Second Brain & Portão JEV

“Valide se este CPF é válido e formate como 000.000.000-00.”
“Interceptado pelo Portão Determinístico (Faixa 1). Algoritmo MOD11 local executado em 0 ms. 0 tokens consumidos.”
“Perfeito. E se o cliente for rejeitado, redija um email empático explicando a pendência cadastral.”
“Classificado como Faixa 3 (Geração com contexto). Injetando regras do negócio e gerando com LLM em uma única chamada controlada.”
✨ Economia de 94% em tokens, latência zero no que é regra determinística e IA aplicada onde realmente cria valor.

02 · A REGRA DE OUROTrês faixas, uma pergunta antes de gastar token

A regra absoluta nº 1 do projeto proíbe usar LLM quando código determinístico ou regras de negócio resolvem. Na prática, toda tarefa é classificada antes de qualquer chamada:

Faixa A · DeterminísticaCálculo, filtro, validação de schema, regex, script. Código puro: 0 ms, custo zero.
Faixa B · Decisão e classificaçãoEscolher entre alternativas finitas ou categorizar eventos. Motor de regras (JEV): cerca de 1 ms, custo zero, totalmente auditável.
Faixa C · Geração e raciocínioProsa, síntese de documentação, código inédito. Aqui sim entra o LLM, com validação obrigatória da saída.

03 · O PADRÃO JEVIdentificar, decidir, validar e só então gerar

1 · IdentificarO software coleta o estado tipado da aplicação: dados da requisição, campos preenchidos, valores numéricos.
2 · DecidirUma camada tipada devolve uma escolha categórica com confiança e justificativa auditável.
3 · ValidarRegras determinísticas confirmam que a decisão é aceitável antes de qualquer efeito colateral.
4 · Gerar (opcional)O modelo generativo só entra se for realmente necessário redigir texto em linguagem natural.

O contrato é pequeno e vale para qualquer linguagem. Em TypeScript:

interface DecisionResult {
  decision: 'PROCEED' | 'REJECT' | 'CLARIFY' | 'ESCALATE';
  ruleId: string;      // rastreabilidade e auditoria
  confidence: number;  // 0.0 a 1.0
  rationale: string;   // justificativa legível
}

Exemplo de fluxo, um serviço de reembolso: o código consulta o motor local primeiro. Se a decisão é PROCEED, executa o estorno sem gastar um único token. Se é ESCALATE, envia para a fila de um auditor humano. Só quando há texto livre a analisar, como a justificativa escrita pelo cliente, o LLM é acionado.

04 · PROVA REALO projeto pratica o que prescreve

O mesmo motor roda dentro do AI Second Brain (scripts/decision-provider.js), síncrono, em CPU, 100% offline. No Quickstart Studio, se o desenvolvedor digita um pedido vago, o motor intercepta antes de qualquer LLM e pede esclarecimento:

> adicione pagamentos→ CLARIFY · JEV-RULE-AMB-PAYMENT · confiança 0,95

A justificativa registrada é objetiva: solicitação de pagamento sem provedor ou métodos especificados. Nada de adivinhar, nada de alucinar.

05 · OBEDIÊNCIAComo a IA da sua IDE respeita isso

O modelo não tem vontade própria: ele segue o contexto que a IDE injeta. Por isso a regra vive em arquivos que os agentes leem sozinhos: o AGENTS.md universal, a skill ai-decision-gate (triagem em 5 passos) e a regra 01-ai-decision.md, que classifica como infração usar LLM em tarefa determinística, chamar IA em loop a cada evento ou ignorar o padrão em decisões e classificações.

Cenário A · Cockpit centralCom a pasta do AI Second Brain aberta na IDE, a governança é carregada 100% automaticamente por Claude Code, Cursor, Windsurf, Cline e outros.
Cenário B · Repositório isoladoSe você abre só o repositório do projeto, ele precisa de uma ponte de governança na raiz (AGENTS.md, CLAUDE.md ou .cursorrules) apontando para as mesmas regras.

07 · CHECKLISTAntes de levar uma feature com IA para produção

  • A tarefa foi classificada: determinística, decisão ou geração?
  • Confirmei que SQL ou código simples não resolvem?
  • A chamada usa a interface IDecisionProvider, e não um SDK fixo no código?
  • O motor local cobre as regras de negócio conhecidas?
  • Pedidos ambíguos retornam CLARIFY em vez de inventar uma resposta?
  • Se o provedor externo falhar, a aplicação segue funcionando com as regras locais?
  • A decisão arquitetural foi registrada em DECISIONS/ do projeto?
Saber quando não chamar um modelo é uma disciplina de engenharia, não uma limitação.
