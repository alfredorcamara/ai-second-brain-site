When AI “cleans up” your code and undoes your optimization

There is an agent error that breaks neither the build nor the tests: the “cleanup” that undoes a deliberate decision. The code looks nicer, and the system gets worse.

AC
Alfredo R. CâmaraCreator of AI Second Brain
📅 November 2, 2026·⚡ Governance & ADRs

The project names this problem: the amnesia of why. Git shows what changed, but it does not explain why a LINQ query became Dapper three weeks earlier. Without that record, the next agent looks at the current code, finds the choice off-pattern and “cleans” it. In this article I take apart how that happens and the layers AI Second Brain uses to prevent it.

01 · THE INCIDENTAnatomy of a silent cleanup

Week 0 You swap LINQ for Dapper with stored procedures to gain performance.Week 1-2 The code works. The reason lives only in your head and in a chat nobody opens.Week 3 New session, another agent: “clean up the data layer”. The agent sees hand-written queries and finds them off the modern pattern. The tests pass: the behavior is the same.Later Latency rises. Nobody connects the two.

Illustrative scenario, based on the example in the project value document. The remark that the tests pass is my own reading.

02 · WHY IT HAPPENSThree causes the project describes

Amnesia of why
Git shows the diff, not the reason. Without ADRs, the agent undoes the optimization thinking it is cleaning the code.
AI-accelerated entropy
An agent with many files open can introduce debt in minutes, such as recreating utilities that already existed or swapping a library midway.
Context drift
Without centralized rules and history, the agent reinvents the wheel, violates patterns and undoes earlier fixes, with silent regressions.

I add a reading of my own: an optimization is usually, by definition, a deviation from idiomatic code. To an agent that only sees the current code, a deviation looks like dirt.

03 · WHAT LOOKS LIKE DIRTFour kinds of code that beg to be “cleaned”

Hand-written query
Dapper with stored procedures instead of an ORM, for performance and legacy compatibility. This is the project example.
Deliberate duplication
Code repeated on purpose to keep two modules decoupled.
Cache and denormalization
Repeated data or data stored in another format to read faster.
Manual loops on a hot path
Less elegant code written to avoid allocations and extra cost.

Only the first comes from the project. The other three are generic examples, written by me.

04 · THE LAYERS OF DEFENSEWhat a cleanup request should pass through

In AI Second Brain, a refactoring request goes through four layers of context before turning into code. If any of them protects the code, the agent respects it or proposes a new ADR.

1 · Master rule
Requires the agent to consult existing decisions in DECISIONS/ before changing a pattern.
2 · ADR
Records the decision, the reason and, if needed, the ban on replacing it without explicit authorization.
3 · CURRENT_STATE.md
Lists what is 100% tested, the sensitive spots where you must be careful and the known bugs.
4 · PROJECT.md and ARCHITECTURE.md
Document the real stack, with exact runtime and library versions, and the project constraints.

05 · LEGACY PROJECTSSix steps to shield what already exists

Scan without changing code→Project satellite folder→Real stack in PROJECT.md→Retroactive ADRs→State in CURRENT_STATE.md→Bridge in the repository

The crucial step is the fourth. The usage guide says that one of the biggest risks of AI in legacy code is “rewriting everything” with modern patterns, such as swapping Dapper for Entity Framework or SQL Server for PostgreSQL. The retroactive ADR example records that the project uses Dapper with stored procedures for high performance and compatibility, and that the agent must never replace it without explicit authorization. The initial scan does not modify a single line of the legacy system.

06 · BEFORE ACCEPTING A CLEANUPA review protocol

  • Does the diff touch anything covered by an ADR? Ask the agent which ADR applies.
  • Is there a sensitive spot in CURRENT_STATE.md in that area?
  • Does the cleanup change SQL, indexes, concurrency or performance? Measure before and after.
  • Cleanups go in separate commits, easy to revert.
  • If the decision really changed, write the new ADR before accepting.
  • Did the agent consult DECISIONS/? If not, refuse and ask it to.

To request the refactoring with the shield already in place, this is the prompt I use as a template:

Before refactoring [file], read DECISIONS/ and CURRENT_STATE.md.List the decisions and sensitive spots that apply to this code.Only then propose changes, without altering what an ADR protects.If you think a decision should change, propose a new ADR instead of the direct change.

And a local signal in the code itself, which the agent sees without having to search:

// ADR-001: Dapper with procedures for performance. Do not replace without a new ADR.

The protocol, the prompt and the comment are written by me. The project does not enforce this format.

07 · HONEST LIMITSWhat the shield does not solve

An ADR is not a technical lock
It is context the agent reads. In a repository opened in isolation, it only sees the rules if there is a governance bridge.
An ADR without the why does not help
“Use Dapper” with no reason becomes dogma. The value is in the reason and the rejected alternatives.
Questioning the decision is legitimate
Decisions can be wrong. The path is a new ADR, not a silent change.
You still need to measure
Documentation does not replace a benchmark. If the optimization is critical, protect it with a performance test too.
