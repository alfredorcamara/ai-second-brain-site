One brain, many repositories: shared governance for all your AI projects

With many projects, the problem is not only each agent forgetting. It is each project having its own way. A shared brain gives everyone the same standard without mixing what belongs to each one.

AC
Alfredo R. CâmaraCreator of AI Second Brain
📅 November 2, 2026·⚡ Architecture & Governance

Imagine three repositories with three different ways of committing, three security policies and three ways of deciding when to call an AI. Each agent works well inside its own project, and the whole becomes a patchwork. AI Second Brain solves this by separating what is common to all from what is specific to each project.

01 · WHAT IS COMMONThe layers shared by all projects

Non-negotiable rules
.agents/rules/: development, security, AI routing and documentation.
Agent skills
.agents/skills/: AI gate, project onboarding, architecture review and memory persistence.
Knowledge base
knowledge/: universal patterns such as AI Gateway, AIJev, OWASP and architecture.
Global memory and decisions
memory/ with current state and lessons learned, and decisions/GLOBAL_DECISIONS.md.

02 · WHAT BELONGS TO EACHEach project has its own contracts folder

projects/<name>/├── PROJECT.md # vision and scope├── ARCHITECTURE.md # formalized architecture├── CURRENT_STATE.md # where the project is today├── DECISIONS/ # project ADRs├── BACKUPS/ # Markdown and JSON exports└── RESEARCH/ # research labs

Memory lives on two levels: the framework one, common to all, and each project one, in projects/<name>/. That way one client context does not leak into another.

03 · A NEW PROJECTJoins the brain in a few minutes

You can create the project from scratch, with an automatic git init, or link an existing repository through an NTFS junction or symlink, without duplicating files. The project-onboarding skill creates the standard structure and the initial contracts (PROJECT, ARCH, STATE and ADR-0001), which you review before saving.

Create or link the repository→Stack interview→Contracts filled in→Project inherits common rules and skills

04 · THE ROUTINESwitching between projects without losing the thread

Each time you switch projects, you tell the agent which one you will work on and ask for the current context. It reads PROJECT.md, CURRENT_STATE.md, the decisions and earlier memories, and returns a summary. At the end, the session-memory skill logs the session. The project two checklists:

Starting a task
  • Read the project PROJECT.md and CURRENT_STATE.md.
  • Check the rules in .agents/rules/.
  • Classify the task before acting.
Ending the session
  • Test the changes.
  • Update the project CURRENT_STATE.md.
  • Update the global persistent memory.
  • Record decisions in DECISIONS/.

05 · GLOBAL OR LOCALWhere each decision and lesson should live

Lessons recorded in the global memory stay available for the next sessions, and decisions that apply to every project go in GLOBAL_DECISIONS.md. Those that apply to just one go in the project DECISIONS/.

A test I use, which is not a project rule: if the decision would still hold if you switched projects tomorrow, it is global. If not, it is local. To see every project at once, the portal has a dashboard with governance status and a 3D graph where each project is a star with its files orbiting.

06 · HONEST LIMITSThe price of having a single brain

A wrong rule affects everyone
Changing a global rule changes the behavior of every project. Record the change as an ADR.
Too many rules stiffen
Projects with different needs may suffer under rigid global standards. Keep the common part lean.
It takes discipline
The start and end checklists only work if they are followed, in every project.
